## 發現的問題

### 1.（中）中文姓名偵測規則對同一姓名的第 3 次（含以上）出現可能漏判

- **現象**：測試檔 `tests/fixtures/sample.txt` 中「王小明」出現 3 次（第 3 句「王小明另提供緊急聯絡人歐陽志遠（手機 +886-955-123-456）。」開頭的「王小明」）。去識別化後僅前兩次出現的「王小明」被標記為 `[姓名:xxxxxx]`（各自不同編碼），第 3 次的「王小明」未被標記，以原文形式殘留於去識別化預覽與（推測）下載文件中。
- **重現步驟**：
  1. 於「去識別化」頁籤上傳 `tests/fixtures/sample.txt`。
  2. 觀察預覽第二段「案件說明：」區塊第二行：「王小明另提供緊急聯絡人[姓名:xxxxxx]（手機 [手機:xxxxxx]）。」——注意行首「王小明」三字未被方括號標記包住。
  3. 以瀏覽器 DevTools／`document.evaluate` 或本次驗證使用的 `javascript_tool` 確認該文字節點屬性為 `<span data-plain="true">洽公。\n王小明另提供緊急聯絡人</span>`，證實該段被判定為「未命中」的原文，而非渲染問題。
  4. 右側「偵測項目」清單中「姓名」類別僅有 5 筆（王小明×2、林美玲、歐陽志遠、陳大文），而非王小明×3 應有的 6 筆姓名項目。
- **影響**：此為去識別化正確性缺陷——同一真實姓名重複出現時，規則命中不具備冪等性／全域一致性，可能導致敏感個資（姓名）外洩於已「去識別化」的輸出文件中，牴觸產品「零殘留敏感文字」的核心承諾。
- **後續切換到停用手機規則、啟用自訂規則後重新上傳同一檔案，此現象仍穩定重現**（第 3 次「王小明」持續未被標記），可排除單次隨機性或編碼衝突導致的巧合，判斷為規則引擎在同一份文件內對重複姓名的匹配存在系統性遺漏（可能與多規則/多次掃描間的位置去重或重疊區間處理邏輯有關，需開發端進一步排查 `src/` 中姓名偵測與位置合併的實作）。

### 2.（低）還原頁籤對「編碼表缺少對應列」情境缺乏明確警告文字

- **現象**：quickstart.md 情境 3 描述「反向測試：故意刪除 CSV 其中一列再還原 → 預期列出無法還原的編碼警告，其餘正常還原。」實測以缺少 `zz9999` 列的 CSV 還原含 `[姓名:a1b2c3]` 與 `[姓名:zz9999]` 兩個標記的文件時，「已還原 1 筆」計數正確、`a1b2c3` 對應的「王小明」正確還原，但 `zz9999` 僅維持原始 `[姓名:zz9999]` 標記文字殘留於預覽中，並未看到任何 toast、警示區塊或文字明確告知「編碼 zz9999 無法還原」。
- **重現步驟**：
  1. 建立 CSV：`code,category,original` 標頭 + `a1b2c3,姓名,王小明` 一列。
  2. 建立文件：`本案由 [姓名:a1b2c3] 與 [姓名:zz9999] 簽署`。
  3. 於「還原」頁籤依序上傳上述文件與 CSV。
  4. 觀察「已還原 1 筆」下方及頁面其餘區域，並用 `document.querySelectorAll('[class*=toast],[role=alert],[role=status]')` 檢查 DOM，均未發現任何提及 `zz9999` 或「無法還原」字樣的元素。
- **影響**：使用者僅能透過「已還原 X 筆」與預覽中殘留的 `[類別:編碼]` 標記自行推斷有遺漏，不符合 quickstart 所述應「列出無法還原的編碼警告」之使用者體驗預期；建議在還原完成後，若有標記未能對應 CSV，應額外顯示明確的警告清單（例如：「以下編碼無法還原：zz9999」）。
- **嚴重性評估**：功能面（還原正確性、計數）本身正確，此項屬 UX／需求符合度落差，非資料外洩或崩潰風險，故列為低優先級。

## 其他觀察（非缺陷）

- 重新整理頁面且尚有未下載文件時，`navigate` 觸發瀏覽器原生「Leave site? / 未儲存的變更」對話框而阻擋導覽，符合 FR-017 資料遺失警告設計預期。
- 偵測規則頁籤刪除自訂規則會呼叫 `window.confirm`；驗證時為避免原生對話框阻塞自動化工具，改以 `window.confirm = () => true` 覆寫後再觸發刪除，屬測試技術手段，不影響對「刪除功能本身正確」的判斷（刪除後規則確實從清單移除）。
- 手動框選新增標記情境改用 `javascript_tool` 建立 `Range`/`Selection` 並於 `.preview` 派發 `mouseup` 事件，而非以 `computer` 工具實際拖曳滑鼠，因程式化路徑較穩定可靠；此為驗證方法選擇，不代表拖曳選取本身有問題（未實測拖曳路徑，故無法對其穩定性下結論）。

## 後續處置（主代理，2026-09-02）

1. **問題 1（姓名第 3 次出現漏抓）— 已修正**。根因並非「重複出現去重」，而是 `zh-name` 規則的姓名後綴白名單（`NAME_FOLLOW`）未涵蓋「另」等接續詞，導致「王小明另提供…」不命中。已於 `src/core/patterns.ts` 擴充常見接續詞（另、也、則、更、不、有、被、將、提供、前往…），整合測試 `tests/integration/roundtrip-text.test.ts` 已驗證 3 次「王小明」皆取得不同編碼；瀏覽器重驗預覽顯示 `王OO` ×3。
2. **問題 2（還原缺編碼無警告）— 非缺陷**。驗證時使用的 `zz9999` 含非十六進位字元，依 `contracts/marker-format.md` 不構成標記，因此不會列入「無法還原」。改以合法編碼 `[姓名:ffffff]` 重測，還原頁正確顯示「已還原 1 筆，1 個編碼無法還原」與缺失編碼清單 `ffffff`（截圖確認）。
